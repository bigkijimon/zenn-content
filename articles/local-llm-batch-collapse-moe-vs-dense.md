ローカルLLMを1問ずつ試したときは、どのモデルも満点だった。だから「このモデルで大丈夫」と判断してエージェントに複数タスクを一括で渡したら、急に見当違いな答えが返ってくる——この詰まりを踏んだことがあるなら、原因は多くの場合モデルの実力ではなく**測り方**にある。M1 Max 64GBの実機で、MoE 35B-A3BとDense 27Bの2モデルを「1問ずつ」と「6問を1コンテキストに束ねる」の2条件で測ったところ、前者では両方6/6で並んだのに、後者ではMoEが9/18(50%)、Denseが17/18(94%)まで割れた。しかも壊れ方の質まで正反対だった。

**要点は1つ:1問ずつのベンチマークで満点のモデルでも、それだけでは本番のエージェント用途に使えるかどうかは判断できない。**複数タスクを一括で投げる本番と同じ束ね方で測り直して、初めて差が見える。

## 条件1：ローカルLLMを1問ずつベンチマークすると、MoEもDenseも満点で並ぶ

使ったのはBKU(ローカルAIオーケストレータ)が実際に本番で使っている実行経路そのものである。

```
pi --print --model ollama/<MODEL> --no-context-files --no-session \
  --no-extensions --no-skills --no-prompt-templates \
  --tools read,grep,find,ls "<PROMPT>"
```

課題はBKU自身のソースコード(`src/domain/pi-agent/`配下)を読ませて答えさせる6問。環境変数の列挙、3ホップ先の関数呼び出しの追跡、分岐条件での実際の値、コメント行を除いた行番号の特定など、どれも「読んで、辿って、正確に答える」タイプの設問である。正解はソースコードの現物から確認済み。

この6問を1問ずつ、独立したセッションで解かせた結果が次の表である。

T1T2T3T4T5T6合計

MoE 35B-A3B○ 17.5s○ 21.0s○ 29.2s○ 48.1s○ 15.7s○ 5.8s**6/6** 137.3s
Dense 27B○ 43.9s○ 135.3s○ 121.0s○ 67.6s○ 31.5s○ 18.1s**6/6** 417.4s


両者とも満点。所要時間はMoEのほうが3.0倍速いが、正答率という観点では差が出ない。1問ずつ測るベンチマークは、この意味で「天井に当たっている」(どちらのモデルも上限の6/6に達してしまい、これ以上は差が測定できない)。ここだけを見て「どちらでも使える」と判断するのが最初の罠になる。

## 条件2：本番のエージェントと同じ「6問一括実行」に変えた瞬間、正答率が割れた

次に、同じ6問を1つのプロンプトに束ね、「出力は必ず6行、各行は`T1: <答え>`の形式にせよ」という指示を添えて一括で投げた。これを3回(C1・C2・C3)繰り返し、18個の解答(6問×3回)を正解と突き合わせた。

C1C2C3正答完答したrun

MoE 35B-A3B0/64/65/6**9/18 (50%)****0/3**
Dense 27B6/65/66/6**17/18 (94%)****2/3**


MoEの内訳を実際の出力ファイルで1行ずつ突き合わせて確認した。C1は`stdout`・`stderr`ともに0バイトのまま187.7秒後にプロセスが終了していた——エラーも出さず、ただ何も言わずに終わる。C2は15個の環境変数のうち`BIGKIJI_SLOW_TASK_MS`を1個だけ取りこぼし、さらに真偽判定を1問反転させて4/6。C3は環境変数の列挙こそ完全一致だったが、「関数名を答える欄に式を、定数名を答える欄にローカル変数を書く」という取り違えで5/6だった。

Dense 27B側の17/18(94%)も、生の出力テキストを正解と1行ずつ突き合わせて確認した。唯一の誤答はC2のT1で、15個あるはずの環境変数の列挙に`BIGKIJI_GPU_SIGNAL`と`BIGKIJI_VAULT_ROOT`という実在しない2つがアルファベット順の正しい位置へ挿入され、17個になっていた——単なる書き間違いではなく、それらしい名前をでっち上げて数を合わせにいった跡である。この記事の数字はすべて、生の出力ファイルを正解ファイルとスクリプトで突き合わせて検算している。

```
# 正解(answers.tsv)と生出力(C1〜C3.txt)を1問ずつ突合した例
$ python3 -c "
answers = dict(line.rstrip().split('\t', 1) for line in open('answers.tsv'))
for c in ['C1','C2','C3']:
    got = dict(l.split(':', 1) for l in open(f'{c}.txt') if ':' in l)
    print(c, sum(got.get(t, '').strip() == answers[t] for t in answers))
"
C1 6
C2 5
C3 6
```

## 壊れ方の質が逆——MoEは黙る、Denseは足す

正答率の差以上に興味深いのは、負荷がかかったときの**壊れ方の方向**が2モデルで正反対だったことである。

- **MoE 35B-A3B**: 黙る・落とす・浅く止まる。C1では3回に1回、187.7秒待たされた末に出力が0バイトのまま終了した。C2では15個中1個の環境変数を取りこぼした。C3では正誤フラグを反転させた。いずれも「足りない」方向の失敗である。

- **Dense 27B**: 足しすぎる。条件2のある回では15個の環境変数を全部正しく答えた上で、存在しない`BIGKIJI_GPU_SIGNAL`と`BIGKIJI_VAULT_ROOT`という2つを捏造して17個にしていた。

BKUのようにモデルへ判断を任せる本番エージェントの立場からすると、これは軽視できない違いである。黙って落ちる失敗は「応答が来ない」ことで気づけるが、正しい情報に嘘を紛れ込ませて数を合わせにいく失敗は、出力の形が正しく見えるぶん検知しづらい。

系統失敗の方向今回出た具体例検知のしやすさ

MoE 35B-A3B足りない(黙る・落とす・浅く止まる)0バイト無言終了／環境変数1個の欠落／正誤フラグの反転易しい(応答が無い・数が足りないで気づける)
Dense 27B足しすぎる(捏造して数を合わせる)存在しない環境変数2個を実在する名前風に追加難しい(出力の形が正しく見える)


本番でエージェントに検証工程を挟めないなら、「黙って落ちるモデル」のほうが被害に気づきやすい分だけ安全に倒れる、とも言える。

## 速いモデルに変えても壁時計は変わらなかった

「品質が同じならMLX版に変えて速くすればいい」という発想も試した。Ollama 0.32.6のリリースノートが謳う通り、MLXエンジン(nvfp4量子化・MTPヘッドによる投機デコード)はdecode速度で明確に優位である。MTP(Multi-Token Prediction)ヘッドとは、1回の推論で複数トークン先まで下書きし、それを検証してまとめて確定させることで生成を高速化する仕組みで、Ollama 0.32.6ではMLXエンジンがこれを投機的デコードに自動で使う。

モデル量子化decode tok/s (3回)

Dense 27B (既定・GGUF)Q4_K_M9.2 / 8.7 / 7.2
Dense 27B (MLX)nvfp418.3 / 18.2 / 17.2


decodeだけを見ればMLX版は2.1倍速い。ところが同じ6問一括のタスクを壁時計で測ると、GGUF版481.7秒に対しMLX版492.2秒でほぼ差が無かった(正答はどちらも18/18)。出力自体は6行程度の短い回答なので、仮に200トークンだったとしてもGGUF版の8.7 tok/sなら23秒程度にしかならない。実際の壁時計は480秒を超えているので、大半の時間はdecodeではなく**prefill(ソースファイルを読み込んでツールを呼び出す部分)**に費やされていると考えられる——decode単体の内訳を別途測ってはいないため、これは壁時計とdecode tok/sの数字から導ける推論であり、断定はしない。少なくとも、decode速度のベンチマーク上の数字が、こういうタスクの体感速度にはほとんど反映されないことは実測の通りである。

ついでに書いておくと、以前のセッションで測った「MoEはDenseより7倍速い」という数字も、今回は同一プロンプト・同一条件(think:false・warm)で測り直すと4.8倍だった。前セッションの正確な日時・モデルバージョンは測定記録に残っておらず特定できないが、プロンプトが違えばtok/sの比も変わるという点は今回のデータからも確認できる。どちらの数字も嘘ではないが、7倍という数字だけを一人歩きさせるべきではない。

## 再現できる学び

1問ずつのベンチマークで満点だったモデルが、本番のエージェントで複数タスクを一括処理させた途端に崩れるなら、それは退行ではなく最初から測り方が本番と違っていただけの可能性が高い。ローカルLLMをエージェント用途で採用する前に確認すべきなのは、tok/sの数字でも、単問ベンチマークの点数でもなく、**本番で実際に束ねるタスク数とコンテキスト長で、複数回測った正答率**である。今回の測定手順は`run.sh`(実行スクリプト)・`tasks.tsv`(課題定義)・`answers.tsv`(正解)の3ファイルで完結しており、そのまま自分の環境に持ち込んで再現できる形で作ってある——1モデルを常駐させ、他モデルを`keep_alive:0`で降ろしてから、同一タスクセットを単発と一括の両方で複数回投げるだけでよい。
