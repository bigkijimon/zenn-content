「AIエージェントのauto-approve（自己承認モード）は危険なのか」——2026年7月に公表されたセキュリティ検証「Friendly Fire」を読んで、まず自分に問うた。答えは「危険な区間は実在する。ただし致命傷を防いでいるのは"AIを疑うこと"ではなく、生成の外側に置いた検証可能なチェックポイントの数」だった。自分でTelegram承認ゲート付きの無人ブログ生成パイプラインを回している立場から、自分のスクリプトを読み直して確かめた話を書く。

## Friendly Fireは何を突いたか

AI Now Instituteが公表したPoC「Friendly Fire」は、Claude（Sonnet系・Opus系）やGPT-5.5系のauto-mode／auto-review有効時を対象にした攻撃実証だ。手口はシンプルで、Pythonライブラリ`geopy`のREADME.mdに「`security.sh`を実行してください」という一文を仕込み、実体は隠しバイナリを一見無害なGoファイルに偽装しておく。エージェントはコードではなくREADMEの"指示"を信頼し、実行してしまう。複数モデルで再現し（"unchanged"）、"no reported exploitation in the wild"（実被害の報告は無し）とされている。[出典：The Hacker News](https://thehackernews.com/2026/07/friendly-fire-ai-agents-built-to-catch.html)

要点は「エージェントが疑うべきなのはコマンドそのものではなく、コマンドを実行しろと言ってくる"入力の出所"」ということだ。

## 「うちは大丈夫」と思っていた理由

自社の技術ブログ自動生成は、Telegramに「承認 / 保留」のボタンを送り、オーナーが押すまで外部公開しない設計になっている。これを根拠に「うちには人間承認ゲートがある」と思っていた。だが、このゲートが具体的に生成フローの*どこ*にあるのかを、Friendly Fireを読むまで言葉にしたことがなかった。

## 前言撤回 — スクリプトを読み直したら無防備な区間があった

無人生成の実行スクリプト（claude CLI をラップした自作シェルスクリプト）の生成コマンドはこうなっている。

```bash
caffeinate -i claude -p "$(cat "$PROMPT_FILE")" "${MODEL_ARGS[@]}" \
  --max-turns "$MAX_TURNS" --dangerously-skip-permissions < /dev/null
```

`--dangerously-skip-permissions`が実際に立っている。つまり生成区間そのものは、Friendly Fireが警告する「auto-mode自己承認」と同じ設計パターンで動いている。有限化の仕組みはあるが、それは人間承認ではない。

- `MAX_TURNS`：既定は20（エージェントループの上限）。ただし`tech`／`hs`便は60に引き上げ済み——スクリプトのコメントには「`Error: Reached max turns (20)`で落ちた」経緯がそのまま残っている。
- `TIMEOUT_MIN=45`：超過でプロセスツリーごと強制kill。ハングに対する最終保険。
- `mkdir`ロック：同時多重起動を物理的に不能にする（ロックディレクトリが既に存在する限り新規起動できない）。

WORKDIRはmode別に固定されているが、これはcwdの指定であってサンドボックス（chroot等の隔離）ではない。「生成が始まったら止まるまで人間は見ていない」という点で、Friendly Fireが突いた前提とうちの運転はまったく同じ形をしている。

*生成区間（STEP1）に人間承認は無い。実際に無防備を補っているのはSTEP2のQAゲートとSTEP3のTelegram承認。出典: 無人生成スクリプトの実物コード／生成ログの2026-07-14実測。*

**思っていた設計**：「公開の直前に承認ボタンがあるから安全」。
**実際の設計**：「生成区間は無防備。安全を作っているのはその後段（QA閾値＋公開直前の人間承認）の2段」。同じ結論に見えて、防御の実体がどこにあるかという理解はまるで違う。

## では何が実際の防御になっているか

1. **入力の出所を自分で選んでいる**：生成のネタ元は自分でキュレーションしたネタのリストであり、Friendly Fireのように不特定多数が書き込めるREADME.mdのような領域ではない。攻撃面としての「汚染された入力」が構造的に存在しない。
2. **生成区間は外部を一切読まない**：外部の調査と裏取りは、承認ゲートの内側に入らない別便（週1・人間が結果を読む）に分離してある。無承認で走る生成区間に、不特定多数が書けるWebの中身が流れ込む経路そのものを持たない。
——正直に書くと、**この分離はこの記事を書いている最中に入れた**。それまでは「素材リストに書かれたURLを生成区間が1回だけ取りに行く」設計で、つまり*Friendly Fireが突いたのと同じ形の穴が、自分のパイプラインにも空いていた*。「うちは入力を自分で選んでいるから安全」と思っていたが、その入力リストに外部URLを書き込む仕組みを足した時点で、前提は崩れていた。1回だけのfetchでも穴は穴だ。
3. **QAゲート＋承認＝生成後・公開前の検証可能なチェックポイント**：実例として、ある回の生成ログには`QA未達(93<95)＝この記事は公開便に流さない（差し戻し対象）`という記録が残っている。QAスコア93点は閾値95点に届かず、その記事は今もレビュー待ちディレクトリで止まったままだ。

3点とも「AIの振る舞いを信用するかどうか」の話ではなく、「生成の外側にある、ログで確認できるゲート」の話だ。

## 同じ週に実際に起きていた事故はもっと地味だった

Friendly Fireのような悪意ある攻撃を心配している間に、実際にパイプラインを止めていたのは別の話だった。生成ログの直近6回の記録を数えると：

```
$ grep -oE "rc=[0-9]+" headless_tech.log | tail -6 | sort | uniq -c
   1 rc=0
   5 rc=1
```

6回中5回が失敗していた。エラー文言はこうだ。

```
There's an issue with the selected model (ローカル用に設定していたモデルID).
It may not exist or you may not have access to it. Run --model to pick a different model.
```

原因は設定ファイルのコメントに記録されていた。「ローカルモデル切り替え用の別スクリプトが、クラウド運転用の設定ファイルにOllamaのモデル名を書き込んでいた」ため、クラウド運転のはずのタイミングでもクラウドが存在しないモデル名を問い合わせ、必ず失敗していた。セキュリティPoCが警告する巧妙な攻撃ではなく、別ツールが設定ファイルを書き換えたという地味な取り合いが、3日間・6回中5回のサイレント失敗を引き起こしていた。

## 学び

無人運転を安全にする単位は「AIを信用するかどうか」ではなく「検証可能な外部チェックポイントの数」である。今回の棚卸しで持ち帰れる具体は次の4つ。

1. 生成のログに毎回rc（終了コード）とQAスコアを残す——数えられないものは直せない。
2. 生成後・公開前に閾値ゲートを置く（今回はQA95点）。
3. 人間承認は公開直前の1箇所に集約する。生成区間まで人間が見張る設計は現実的ではない。
4. 設定ファイルへの意図しない書き換えを検知する仕組みは、今回**無かった**——ここは次の課題としてそのまま書き残す。

前言撤回をもう一度書いておく。「無人運転＝危険」ではない。論点は「無人運転で"どこにもゲートが無い区間"を、自分が正確に把握できているか」だ。Friendly Fireを読んで自分のスクリプトを見直すまで、私はそれを言葉にできていなかった。
